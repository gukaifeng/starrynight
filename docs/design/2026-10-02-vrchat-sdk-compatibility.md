# VRChat 角色开发包自动导入：可行性与完整方案

日期：2026-10-02。项目基线：客户端提交 `82e0a03`，实际源码和当前发布名册优先于旧技能参考。

## 1. 目标与结论

用户明确要求：识别作者为 VRChat 发布的角色开发包，下载后可通过统一流程导入星夜；不要求星夜与 VRChat 的运行效果完全相同。随后明确最终交付：App 发现/商城页展示图片、基本信息和演示视频，完整角色内容放在服务端或 OSS，用户选择后下载并应用到对话；除外部下载吞吐外，其他步骤尽可能快。

用户进一步明确产品边界：**作者源包只作为制作输入；先预处理为星夜自有内容格式，再由服务端/OSS 分发。** 普通用户界面、下载/安装和角色控制只使用星夜术语与协议，不出现源 SDK 安装、Prefab 选择、来源参数或平台操作。角色资产和星夜角色定义仍分开管理；必要署名/许可保留，源平台信息和详细转换诊断主要留制作侧。该要求不改变来源追溯与已有角色身份。

**该目标技术上可行，现有代码已提供可复用的核心转换能力，但目前还不是任意开发包的自动导入产品。** 需要补齐通用入口、基于包结构的选择与依赖诊断、明确的降级策略、独立内容构建，以及 App 的动态角色加载。

整个产品有两条流程，源资产转换只出现在生产/上架阶段：

> 制作侧：下载作者源包 → 自动识别/转换 → 验证人物及对话配置 → 生成图片、视频和移动端成品 → 上架。

> 用户侧：发现/商城看图片、信息和视频 → 选中角色 → 授权并下载成品 → 加入角色库并进入对话。

完整且属于支持范围的包应自动处理；同包存在多个合理外观时，让用户选择外观。只有衣服/补丁、缺基础网格或缺必要贴图的包应说明缺什么。特殊光效、原平台交互或不支持的菜单可以按已声明策略关闭或替代，完整本体不应仅因缺平台默认动作就被迫拒绝。

“App 导入”首先实现为选择并下载已经发布的角色成品，不要求用户操作 Unity、等待来源转换或上传开发包。个人文件导入可在未来复用制作侧管线，不作为本次核心用户入口的前置。转换后的角色动态增加，不必每增加一个模型就重新编译和安装 App；这一能力目前尚未实现。

本轮完成官方文档及源码调查和方案编写，没有实施新导入器、启动 Unity 转换或新增真机验证。现有工作区有其他客户端 UI 开发，本轮仅新增本方案。

## 2. 官网核实与可复用基础

用户提供的 [https://creators.vrchat.com/sdk/](https://creators.vrchat.com/sdk/) 是 VRChat 官方创作与 SDK 入门页。SDK 通过 Unity / Creator Companion 组织 Avatar 和 World 的制作；本方案聚焦 Avatar 作者源资产，Worlds/Udon 不是角色导入所必需。

VRChat 官方制作版本目前为 [Unity 2022.3.22f1](https://creators.vrchat.com/sdk/upgrade/current-unity-version/)，入门页说明 VRChat 不使用 URP/HDRP。星夜生产工程当前为 Unity **6000.3.25f1 / URP 17.3.0**。来源解析/构建与生产工程应分开，最终在星夜版本与移动端 profile 下交付内容。

当前 `assets/characters/active-roster.json` 有 **41 个角色条目**。[整库状态](../verification/vrchat-batch-import/library-status.md)记录用户目录的 40 条来源，另有之前独立导入的豆日向；其中很多条目仅有外观预览，名册数量不是完整功能兼容率。

| 环节 | 可以复用的代码/证据 | 仍需完成 |
| --- | --- | --- |
| 档案解析 | `vrchat_batch_audit.py`、`audit_vrchat_archives.py`；ZIP/RAR/7z、嵌套 unitypackage、源哈希与有界展开 | 面向单次用户导入的统一入口和错误结果 |
| Prefab 识别 | `plan_vrchat_library.py` 识别嵌套 Descriptor、Prefab 引用和变体 | 移除对角色名字/目录名的核心依赖，处理多候选和本体＋服装组合 |
| 来源检查 | `vrchat_batch_stage.py`、`VrcSourceInspector`、`VrcPortableGeometry` | 全量依赖闭包、未知骨架、来源组件能力报告 |
| 网格/动画转换 | `vrchat_portable_convert.py`；GLB、蒙皮、morph、作者有效默认状态与 Humanoid 采样 | Generic 类型、非线性 morph、明确的外观导入模式 |
| 材质 | 固定 lilToon 2.3.4、材质属性及纹理映射 | 常见其他 Shader 的映射及特殊屏幕/光效的默认降级 |
| 菜单/动画图 | `vrchat_controls.py`、原生 Mecanim、`AvatarControlDriver`、`AvatarStateBehavior` | 统一缺依赖处理、已识别行为组合回归；完整控制不作为显示本体的前置 |
| MA/NDMF | 已有固定依赖的隔离 bake、保存及 GUID/fileID 交叉核对 | 封包 provenance 接通、允许的依赖版本与具体许可核验 |
| 校验与打包 | XCP schema、seal、`package_vrchat_library.py`、`PortableAvatarReview` | 导入结果分级、运行内容构建、成品版本与缓存契约 |
| App 加载 | 已编译角色的 `Resources.LoadAsync`，角色隔离与淘汰 | 导入页、动态目录、私有内容包下载/安装/删除与恢复 |

重要现状：`plan_vrchat_library.py` 仍有 `PREFERRED`、名字评分及角色专用联合来源规则；`scripts/import_character.py` 导入 XCP 后仍要求 Unity 构建并明确提示不会修改已安装 App。因此现阶段是开发工具链，尚未达到用户下载开发包即导入的产品目标。

## 3. 输入范围与结果定义

### 输入

制作侧第一版支持作者发布的 ZIP、RAR、7z、`.unitypackage` 和完整 Unity 源目录。允许多个配套文件一起选择，也允许后续给已识别本体补服装/依赖包。FBX-only 作为简化输入提供基础预览，但不能把它当作完整作者 Prefab 外观。App 普通用户下载的是这些来源处理后的星夜内容包。

读取网格、贴图、材质、Prefab、Avatar/骨架、动画、Controller、菜单和参数数据。来源的 C#、DLL、Editor 扩展先记录为依赖，不自动执行；只有明确维护的受信构建插件进入隔离转换阶段。

输入是作者源包。平台 Avatar ID 或已上传的 PC/Android 成品不作为第一版输入，也不等于拥有可导入源数据。

### 结果

| 结果 | 用户得到什么 | 是否计入导入成功 |
| --- | --- | --- |
| 就绪 | 可用人物、默认穿搭、支持的表情/动作和标准互动 | 是，报告明确保留能力 |
| 就绪，部分效果已适配 | 人物完整；特殊 Shader、原平台动作/物理等被显式替代或关闭 | 是，单列降级范围 |
| 需要选择 | 同包有多个合理人物/服装变体 | 待选择后继续，不视为程序错误 |
| 需要补文件 | 缺本体、基础网格、必需贴图或不可恢复的构建依赖 | 否，列出实际所需文件 |
| 当前不支持 | 已识别类型/依赖超出支持范围或预算，无法产生可靠人物 | 否，保留报告供扩展适配器 |

人物导入、完整原作控制、AI 人设/音色是不同能力。导入后的来源能力必须写入清单，界面只显示真实可用选项。不能凭 Humanoid 骨架推断已具备闭眼、口型或所有动作。

## 4. 统一处理流程

### A. 来源审计与主角色识别

1. 展开档案到隔离工作目录，保留路径/GUID/哈希，不修改作者源包；限制展开大小、递归和路径逃逸。
2. 建立资产索引：GUID＋fileID、文件类型、Prefab 继承、网格/材质/纹理引用、Controller 和构建插件依赖。
3. 从实际 Prefab 图中查找 AvatarDescriptor，沿嵌套引用识别实例；没有 Descriptor 时以有效蒙皮和骨架建立简化候选。
4. 基于结构判断本体、服装、补丁和变体。骨架/Renderer/材质闭包完整、作者默认状态有效的候选优先；目录名只作显示信息和辅助提示。
5. 唯一合理候选自动选择；多个合理候选给出缩略预览和来源外观名称。避免默认把裸素体或无关附件当成成品人物。

稳定身份使用系统生成的 avatar UUID，而非 ZIP 名字；源内容哈希用于去重和缓存。更新同一角色通过显式版本关联保留用户身份与设置，不能靠同名文件推断覆盖关系。旧发布角色 ID 保持兼容。

### B. 依赖闭包与构建插件

区分三类缺口：

- **本体必需**：实际可见的网格/贴图、作者组装后才有的身体等，缺失则要求补包。
- **可替代运行效果**：VRChat 平台默认动作、特殊光效、追踪/多人参数等，按兼容策略映射到星夜或关闭。
- **来源构建插件**：MA/NDMF 等，固定版本执行受信构建或由已验证解析路径处理；未知必要插件要求适配，不能忽略后假称默认外观正确。

依赖只在完整且哈希一致的来源间合并。作者分开的本体＋lilToon 版本可以联合索引；跨档案重复 GUID 出现不同内容时提示冲突。已启用、动画可达和仅闲置参考的资源要分别判断，不能一遇到外部 GUID 就拒绝整个包。

构建回执绑定所有来源、所选 Prefab、工具和依赖版本。MA 生成资产必须真正落盘并通过引用交叉核对；不能手改 stamp 绕过检查。现有 Ramune 恢复 71 项控制/6 个控制器/109 层的 [构建记录](../verification/vrchat-batch-import/modular-bake.md)证明这类来源可处理，但它的完整动态能力仍未完成。

### C. 默认人物与移动端转换

以作者主 Prefab 的有效状态为基准，保留嵌套覆盖、Renderer 开关、材质槽、默认形变、正确骨轴和米制比例。优先得到穿着正确、脸部正常、姿态稳定的人物。

| 来源能力 | 第一版默认处理 | 后续增强 |
| --- | --- | --- |
| 网格、贴图、蒙皮 | 转换 GLB，验证骨架和材质绑定 | 更广泛 Generic / 特殊蒙皮支持 |
| lilToon | 复用当前固定宿主版本及受支持属性 | 补高频缺口和 Metal 对照 |
| Poiyomi/其他 Shader | 识别材质类型，映射可支持的基础属性；转换不足时报告并给预览结果 | 用可维护的材质适配器扩展，不要求全部效果等价 |
| VRChat 默认动作依赖 | 用明确属于星夜/授权来源的站姿、待机及对应宿主行为；不会影响人物外观的缺动作可关闭其选项 | 逐类补标准动作和语义映射 |
| 作者动作、表情、穿搭 | 依赖齐全且支持的控制保留 | 更复杂图及组合行为 |
| 口型、眨眼 | 读取 Descriptor/有效 morph 映射；不存在时不伪造 | 新类型面部绑定 |
| 头发、裙子、耳尾 | 现有受限次级运动；不支持的动态保持稳定外观 | 更多碰撞/约束适配 |
| 粒子、屏幕、平台触碰 | 默认关闭无法稳定支持的特殊效果，必要时固定为可解释的显示状态 | 高频效果逐项增加 |
| Generic/无头骨模型 | 原型阶段验证基础显示和视角；首版不承诺全部拟人交互 | 正式扩展非 Humanoid profile |

特殊功能失效可以降级；身体、脸部、默认服装错误则应阻止自动完成或给明确预览选择。若必须优化包体，先裁减未用资源和重复贴图，再处理纹理分辨率；任何影响外观的优化记录到报告，源文件保留。

继续沿用 [XCP 与便携 Avatar 标准](../character-standard/09-portable-avatar-standard.md) 的预算，不为了接收模型放宽全部运行限制。VRChat 自己的 [iOS 指南](https://creators.vrchat.com/platforms/iOS/) 和 [性能等级](https://creators.vrchat.com/avatars/avatar-performance-ranking-system/) 也区分移动端与 PC；本方案允许移动端效果适配，不以 PC 全特效作为验收要求。

### 实时动捕与追踪相关资产

VRChat 支持由头显、控制器及身体追踪器提供的实时姿态输入，见 [全身追踪说明](https://docs.vrchat.com/docs/full-body-tracking)。普通角色源包主要提供接受这些输入的骨骼、绑定、参数和控制逻辑；实时使用者的追踪数据通常在运行时产生，不是角色包自带的一套持续动作。包中也可能另外附有录制动作或示例数据，不能仅凭“支持动捕”判断其内容。

| 内容 | 星夜导入策略 |
| --- | --- |
| 骨骼、蒙皮、面部形变 | 按支持的资产类型识别和保留；这些也是播放动画、口型和表情的基础，不因没有实时动捕而删除 |
| 已录制成 FBX / AnimationClip 的动作 | 按普通动画处理，验证骨架、曲线和依赖；播放动作不要求用户连接动捕设备 |
| 实时头、手、身体追踪及相关 IK / 参数分支 | 当前 App 没有 VR 设备输入，按固定对话宿主上下文适配；保留可用动画，对仅依赖缺失输入的功能关闭或替代，并记录能力差异 |
| 面捕映射、第三方追踪插件 | 有已支持的适配器时转换；未知配置和代码记录为未支持依赖，不宣称任意插件都能运行 |

[Animator Tracking Control](https://creators.vrchat.com/avatars/state-behaviors/#animator-tracking-control) 可让身体部位由追踪或动画驱动，并控制眼部模拟和口型。因此不能笼统删除所有 tracking 字段：它们可能影响眨眼、说话口型及作者动作的优先级。当前 `vrchat_controls.py` 已读取 tracking 字段，`vrchat_host_context.py` 已按非 VR、静止对话环境处理控制图；这只证明部分识别与适配基础，并非完整实时追踪兼容。

上架验证应确认没有实时设备输入时人物姿态稳定，表情和对话口型可正确恢复，不把 T / IK 校准姿势当作正常待机。只因可选动捕功能不可用，不拒绝完整人物；若追踪或未知插件与默认外观强绑定，必须适配并验证，无法得到可靠默认人物时给出需要处理的结果。处理发生在制作侧，App 仍只下载已验证成品，不在用户选中角色后临时解析 VRChat 追踪逻辑。

手机并非无法做任何动捕：[ARKit 支持摄像头面部追踪和表情驱动](https://developer.apple.com/documentation/ARKit/tracking-and-visualizing-faces)。这属于独立的输入能力，需要设备支持与角色映射验证，不作为本轮角色导入或快速进入对话的前置。

### 前摄视觉动捕扩展（可行性调查，尚未实现）

用户进一步询问是否可访问 iOS 前摄像头，让角色实时跟随用户动作。技术上可做，属于星夜新增的实时输入能力，不要求迁移 VRChat 的设备追踪运行系统。

| 路径 | 相机与输出 | 对星夜的意义 |
| --- | --- | --- |
| Apple ARKit `ARFaceTrackingConfiguration` / `ARFaceAnchor` | 前摄；头部姿态、面部表情系数等，按 `isSupported` 判断设备支持 | 首个原型优先实现转头、点头、眨眼、张嘴及来源具备的表情 |
| Apple Vision 身体/手部姿态请求 | 分析提供的图像/视频帧，前摄帧可作为输入；人体/手部关键点，另有 3D 人体姿态估计 | 用于前摄身体和手部跟随，仍需姿态求解、骨骼重定向与时序稳定处理 |
| Google MediaPipe iOS Pose / Hand / Face Landmarker | 支持摄像头实时流；身体提供 33 个关键点及估计 3D 坐标，脸部可输出表情系数 | 身体跟随的另一个可验证候选；结合自身模型和设备推理开销评估，不先假定比 Vision 更快或更准 |
| Apple ARKit `ARBodyTrackingConfiguration` | 后摄的身体追踪 | 不能直接当作用户前摄自拍动捕的实现 |

依据：Apple [前摄面部追踪](https://developer.apple.com/documentation/arkit/arfacetrackingconfiguration)、[面部姿态与表情](https://developer.apple.com/documentation/arkit/arfaceanchor)、[3D 人体姿态介绍](https://developer.apple.com/videos/play/wwdc2023/111241/)、[后摄身体追踪](https://developer.apple.com/documentation/arkit/arbodyanchor)；Google [iOS 身体追踪](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/ios)、[iOS 手部追踪](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/ios)、[iOS 面部追踪](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/ios)。Vision/MediaPipe 识别关键点不等于已经得到适合任意角色的完整动画。

正常手持自拍优先保证脸和头部；拍到肩、手臂时才能评估上半身跟随。全身模式需要放稳手机并让全身进入画面。单目图像的深度、肢体遮挡、快速运动和不可见关节存在估计误差，不能承诺与多追踪器或专业动捕逐动作完全相同。实时跟随还需统一相机方向、镜像/左右、角色骨轴、比例及中立姿态，并在低置信度或丢失追踪时平滑恢复。

实现建议为本地链路：前摄帧 → iOS 姿态/表情识别 → 角色能力映射、校准和滤波 → Unity 宿主驱动。无需把逐帧视频上传业务服务器或等待云端推理；用户开启功能时才请求相机授权。多个识别任务应共用单个相机拥有者提供的帧，不让 ARSession 和另一采集会话同时争抢前摄。

导入阶段增加版本化的表情系数/骨骼映射数据；保留来源具备的表情形变与受支持动作所需骨骼。VRChat 的口型/表情名称不能假定与 ARKit 完全一致，模型只有少量表情时只能跟随相应范围，识别算法不能自动补出缺失形变。映射属于轻量数据，不意味着将原平台实时追踪系统打进每个角色包。

宿主区分对话表现与用户跟随的控制所有权，避免 AI 口型、自动眨眼、原作动画和用户实时姿态同时写入同一部位；退出跟随模式后恢复原行为。当前源码未找到 ARKit / Vision / MediaPipe 实时追踪链路，已有眼/口 ownership 和原作控制适配只提供部分基础。

首个原型用支持的 iPhone 验证单角色面部/头部跟随，再对前摄身体路径做同条件比较。采集/推理频率与 Unity 渲染频率分别测量，记录端到端延迟、抖动、丢追踪恢复、内存、发热和持续渲染表现；不能用 SDK 有实时流接口就宣称完整星夜已达到某个 FPS。模拟器不作为相机动捕性能或效果的验收依据。本轮只调查和补充方案，没有开启用户相机或新增实现。

这不是同一角色“全部功能”与“部分功能”的 A/B 测试：源档案包含可编辑/重复素材，现有 XCP 又混合不同适配程度和外观预览；格式、所选内容和制作文件排除共同影响结果。不能将上述 35.9%–89.1% 当成只关闭动捕的收益，也不能宣称这些角色完整兼容所有原作能力。41 个已发布条目的本地 XCP 总文件大小约 3,545.65 MiB，单个范围 8.53–234.43 MiB，中位数 74.51 MiB；这些同样不是最终 iOS 下载包或运行内存。

样本中 `avatar-controls.json`、`avatar-descriptor.json`、`secondary-motion.json` 和 `physics-source.json` 合计约 0.03–1.05 MiB（仅计存在文件），代表一组控制/追踪/物理配置，不能全部算成实时动捕成本。大幅改变包体的主要候选是额外纹理/网格、制作副本、重复资源及较大的动作数据；删除几个追踪字段通常不是有效减包策略。

纹理尺寸和移动端格式的收益另算。按 Unity 官方 [ASTC 格式说明](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/textureformat) 的 6×6 像素/128 bit 块推算，一张方形纹理连完整 mip 链，4096×4096 约 9.50 MiB，2048×2048 约 2.38 MiB。它说明同格式下缩小分辨率可以显著减少纹理载荷，但不是 PNG 压缩大小或经过 bundle 压缩的实际网络字节数，也不代表近景画质可接受；脸、眼、头发不能一律缩小。

原型阶段应构建同一角色、相同纹理质量/格式的“全部受支持功能成品”与“默认外观＋对话核心成品”，分别报告网络字节、安装占用、扩展内容增量、首帧耗时和功能差异。单独测试纹理优化，避免将画质降低、功能裁减和去除制作文件混成一个收益数字。基础包与按需扩展的依赖由实际图确定，不能把仍被核心引用的衣服/动作仅移动文件后声称首次下载已减小；参见 Unity [避免资源重复](https://docs.unity.com/en-us/engine/6000.0/manual/assets-and-media/assets-managing-runtime/assets-avoid-duplication)。本轮仅静态测量和补充方案，没有生成新的 iOS bundle 或进行设备性能测试。

保留现有 XCP 清单、GLB、材质/动作/控制/次级运动 sidecar。新增导入回执与能力报告的版本化 schema，记录：

- 来源哈希、角色 UUID、源版本、主 Prefab 与依赖。
- 转换器/Editor/Shader/plugin/runtime profile 版本。
- 保留、替代、关闭和缺失的能力及对应用户说明。

源哈希＋选择＋依赖＋工具版本＋目标 profile 相同才能复用转换结果。私有内容的访问权按账户控制；内容哈希相同不代表其他用户获得访问权限。最终安装使用候选→验证→原子生效，失败保留原角色版本。

## 5. App 动态加载设计

当前角色来自编译后的 Resources，`ModelDescriptor.all` 和 bundle 目录需要扩展为统一角色注册表：内置角色＋账户可访问的导入角色。本轮不直接修改它们，已有 UI 工作区改动需保留。

建议第一条交付实现：**保留 XCP 为交换/校验格式，再按星夜生产版本生成每角色 iOS 原生内容包。** 模型、AnimatorController、材质和已认可的宿主组件可以一并构建为 AssetBundle/Addressables 内容，复用现有 Editor 控制器生成器，降低在手机上重写整套 Animator 构建的成本。

Unity 官方说明 [AssetBundle 保存平台相关的非代码资源](https://docs.unity3d.com/6000.0/Documentation/Manual/AssetBundlesIntro.html)。成品必须由星夜自己的内容工程按 iOS 和匹配的组件/引擎版本构建；PC/Android 成品不能直接加载到 iPhone，包也不能给 App 增加未编入的运行代码。

后续若有值得验证的需求，再考虑让部分 GLB/JSON 能力在设备端直接加载，减少内容构建依赖；第一版不同时实现两套完整路径。Addressables/AssetBundle 的确切选型、材质变体及 Animator 绑定以原型结果确定。

动态内容还需固定 `runtimeProfile`、目标平台、内容构建引擎版本和最低 App 能力版本。首版选择严格匹配的内容版本，避免依赖未经测试的引擎兼容性。原型必须确认 IL2CPP 裁剪后仍保留已允许的宿主组件，以及 lilToon Shader 变体、Animator/StateMachineBehaviour 和跨包引用可正确加载；不能只验 mesh 显示。宿主通过明确的保留配置及已编入的组件白名单承接这些资源。

客户端增加：

1. 远程目录、发现/商城图片与视频预览、选择角色、下载状态和加入角色库。来源文件选择/依赖处理属于制作侧入口。
2. 内容下载、哈希验证、安装、取消、失败重试、离线缓存及删除模型。
3. 统一加载接口覆盖 Resources 与导入内容，继续最多保留少量角色实例和取消过期加载。
4. 稳定 UUID、版本化用户控制值、显式升级迁移；不修改其他角色的偏好和聊天。

新增在既有能力范围内的模型只发布内容包。新增运行组件或不兼容能力时才升级 App。可用列表由内容注册表读取，不要求每次编辑发布名册、生成 Xcode 工程或修改 Unity 主场景。

| 封面、头像与预览 | 发现卡片封面、详情横幅、角色头像、缩略图、截图集、演示视频/封面帧、裁切焦点、图片尺寸及媒体来源/版本 | 浏览阶段独立下载和缓存，不等完整模型；发布媒体应对应所引用人物和产品定义的实际版本 |
| 音乐与环境声音 | 专属音乐、环境音、宿主音效、曲目目录、资源引用/哈希、循环、默认值和语音压低音乐政策 | 共享同源文件时只读复用；真实用户当前音量、启停和选择不写回发布定义 |
| 可用内容与作者默认值 | 对 A 能力的开放子集、允许的动作/换装、声音、环境、音乐目录，默认组合；明示创作者可定义项及使用者可调整项 | 列表必须经过服务端/宿主校验；不能开放 A 不具备的功能或由使用者偏好覆盖固定作者定义 |
| 发现/商城发布信息 | 私有/公开/不列出状态、上架状态、分类推荐、版本说明；未来商城需要时的免费/价格/权益产品关联 | 可展示信息通过目录 API 提供；所有权、审核、价格和权益以服务端记录为准，购买记录/动态统计不封入不可变模型文件 |
| 关联与交付版本 | 所引用 A 的确切资产版本、角色定义版本、媒体/声音/环境版本、最低 App/runtime 能力、内容清单、发布版本及回滚关联 | 用发布清单绑定一套一致内容，不能临时混用新模型和旧表情映射；旧角色 ID 保留 |

分类以来源和职责为准，不以扩展名为准。例如作者角色上的原作粒子/SFX 属于 A；星夜为对话场景添加的花瓣和萤火属于 B。作者预览图可作为来源媒体保留，再由 B 选择作为封面。两部分可以引用同一个物理文件，不要求复制素材；媒体来源标签不因作为星夜封面而改变。

### 两部分的关联与版本

建议新增 `avatarAssetId` 表示可复用模型资产，保留现有角色/实例 ID 表示星夜中的独立角色。一个角色定义引用一份明确版本的模型资产，同时引用对应的人设、音色、背景和媒体。以下仅为关联示意，不是已落地 API/schema：

```json
{
  "characterId": "character-<existing-uuid>",
  "definitionVersion": "1.0.0",
  "avatarAsset": { "id": "avatar-<uuid>", "version": "1.0.0", "runtimeProfile": "<supported-ios-profile>" },
  "personaRef": "persona-<uuid>",
  "defaultVoiceRef": "voice-<uuid>",
  "presentation": {
    "coverRef": "media-<cover>",
    "avatarRef": "media-<portrait>",
    "previewVideoRef": "media-<demo>"
  },
  "scene": { "backgroundRef": "media-<background>", "effectProfileRef": "effect-<uuid>" },
  "releaseId": "release-<uuid>"
}
```

同一个外观可以关联两个不同的星夜角色，拥有不同的人设、声音、封面和背景；两个角色不因此共享私聊、记忆或使用者偏好。换封面、介绍、背景或音色不应触发模型重下载；新增的背景/音频各自下载。更改模型/贴图/动画才发布 A 的新版本，并重新验证 B 的动作和表情引用。更新人设或声音时，服务端已有候选/音频缓存按实际依赖失效，而不是改文件名绕过版本。

星夜角色上架为“可对话”前，人设、已批准音色、表现语义、核心模型及所需媒体都已关联并验证；用户选择时不等待创建音色、制作人设或源包转换。只有外观的候选可进入明确标注的预览区，不应展示为已经可聊天。

### 不属于两部分发布内容的数据

聊天记录、用户记忆、真实关系/故事进度、针对用户生成的语音和预备回复、个人静音/音量、个人允许的偏好、收藏/购买记录，以及摄像头实时帧/识别结果分别保存为使用者数据或瞬时运行数据。其持久作用域按账号和角色实例隔离，不能写入 A、公共 B、封面或另一个用户的记录。创作者定义角色的权限与听众允许调整的项目继续遵守现有 [角色集合标准](../character-standard/character-collections.md)，不因这次资产拆分扩大编辑权限。

供应商凭证、管理员信息及可执行服务逻辑也不属于可下载角色数据；目录、AI 人设/音色管理、发布授权和用户数据仍由 `../starrynight-server` 管理，本仓库仅维护客户端协议/加载与制作标准。

### 存储、下载与现有格式迁移

- **发现阶段**：读取 B 的公开介绍和轻量预览媒体，角色封面/头像/视频独立缓存，不先下载 A。
- **选择阶段**：服务端一次解析权限及一致发布清单，给出 B 的客户端配置、A 的核心成品和必要场景资源；二进制直接从 OSS 下载。私有人设和供应商音色管理信息不下发。
- **进入对话**：优先使用已缓存的 A；先满足真实默认外观与核心对话依赖，扩展外观、音乐等按需加载。两部分的逻辑边界与物理分包大小是不同问题，需要同角色构建测量。
- **更新阶段**：A、B 和媒体独立版本化，以 release 关联一套已验证内容；公共资源按内容哈希复用，但缓存存在不能替代访问授权。

现有 [CharacterManifest](../../unity/CharacterRuntime/Assets/Scripts/Runtime/CharacterContract.cs) / [XCP schema](../../character-sdk/schemas/character.schema.json) 同时包含 `display`、`effects`、`interactions`、`behaviors` 等字段，尚不是两部分完全隔离的协议；[CharacterCollections.json](../../ios/CharacterHost/Resources/CharacterCollections.json) 已将声音、音乐和环境目录与模型引用关联，服务端又单独维护人设/故事。迁移先建立独立来源定义和星夜定义，并生成兼容当前宿主的受控组合配置；不要当场删除旧 schema 的必需字段或重命名角色 ID。之后随协议版本升级逐步拆出混合字段，并回归现有角色。

### 固定转换程序与异常处理

用户询问应以固定程序转换角色包，还是依靠 AI 逐包分析。采用**固定、版本化的来源转换程序**作为生产路径：结构化解析、受支持适配器、引擎构建和校验不依赖大模型推断，不为每次来源转换自动调用 AI。AI 可在开发/维护时帮助调查未知类型并实现可复用适配器，不作为用户下载或正常转换的必需服务。

现有 `vrchat_batch_audit.py`、`inspect_vrchat_library.py`、`vrchat_portable_convert.py`、`package_vrchat_library.py` 等已用脚本/Unity 完成主要步骤。`plan_vrchat_library.py` 仍使用 `PREFERRED`、名字评分和个别角色联合来源分支；预览封包也有部分角色专用规则。它们是待替换或归并的已知适配，不能作为任意新角色包自动转换的完成证据。

| 环节 | 固定程序的职责 | 需要处理的例外 |
| --- | --- | --- |
| 输入与索引 | 有界展开 ZIP/RAR/7z/unitypackage，解析资产类型、GUID/fileID、依赖与哈希 | 缺文件、损坏/冲突档案按实际原因报告，不凭同名资源补齐 |
| 人物选择 | 按 Descriptor、有效骨架/蒙皮、默认外观和引用图识别本体与变体 | 有多个合理候选时给预览选择；衣服包不能被误当完整人物 |
| 来源组装 | 合并完整依赖，处理嵌套 Prefab/覆盖；调用固定受信 MA/NDMF 等适配 | 未知必要构建插件输出需要适配，不自动执行作者任意代码 |
| 资产与行为转换 | 以类型/版本适配器转换网格、形变、材质、动画、控制、物理和约束 | 未支持且影响默认人物的类型需要处理；可选效果按声明的策略关闭/替代 |
| 构建与校验 | 生成星夜格式，构建目标平台成品；校验引用、默认状态、能力、预算和版本，输出渲染预览/检查结果 | 静态校验不能证明视觉正确；异常外观和新类型仍需制作方检查，不能以 AI 自信判断替代 |
| 产品关联与发布 | 将制作方提供的 B 定义和已有声音/媒体关联，生成一致的发布清单 | 没有人设/已批准音色的模型只能报告资产就绪，不能冒充已可对话；发布由既定服务端流程执行 |

转换程序由命令行入口和明确模块组成，可由制作后台提交任务，内部按需调用 Unity/Blender；不要求整个流程只用一段纯 Python。固定输入、来源选择、目标 profile、依赖和工具版本应得到可复现的能力与转换结果，保存回执供重跑。结果至少区分：资产就绪、角色就绪、需要选择、需要补文件、需要适配、转换失败；不会把所有问题统一变成“找 AI 处理”。

扩展覆盖的方法是从失败报告提炼通用类型支持，例如新增某种 Shader 或构建组件的适配器，并用可复现案例和现有角色回归验证。适配器按资产结构/组件类型/版本选择，避免每增加一个角色就增加一段按角色名字判断的代码。确有来源缺陷必须个别修复时，保存显式选择/修复配方及来源哈希，不把它推广成对任意缺失引用的默认忽略。

AI 人设/声音/媒体制作与模型转换分别计状态和成本。本方案优先使用制作方已配置人设、已批准音色及现有图片/音频，不自动调用图片模型或创建付费音色。转换 worker 在上架前工作；普通 App 用户仍下载现成内容，不等待源包转换。未知类型需要适配的情况不会阻塞已发布角色的下载和对话。

### 星夜专用交付格式与来源预处理

交付协议建议标识为 `starrynight.character-content`，以 `schemaVersion` 管理格式版本。此处定义目标契约，尚未新增实现或上传 OSS。星夜拥有包结构、字段语义、能力协议、版本关联和加载流程；底层复用目标平台内容包、GLB、移动端纹理及通用音视频格式，不需要重新发明几何/纹理编码。XCP 可继续作为制作中间格式和校验依据，用户无需认识它或源平台格式。

制作侧按以下顺序产出成品：

1. **读取与追溯**：在私有目录保存原档案、来源哈希、选用人物和依赖；维护源 GUID/fileID、路径与生成资源 ID 的映射。
2. **提取有效人物**：计算默认外观与可用控制依赖，得到网格、骨架、形变、材质、原创动作和可适配效果，排除制作副本和不交付的平台实现。
3. **转换数据和行为**：将口型、表情、衣发运动、控件和可用控制图转成星夜的绑定及能力协议。给公共控制使用稳定的语义 ID 和界面标签，源 `GestureLeft`、tracking、SDK 类名等不作为产品接口直接暴露。不能机械删除 tracking 字段或改骨骼/形变名破坏绑定；原名称可留内部，重命名时需同步重定向所有引用并验证。
4. **关联星夜定义**：绑定已准备好的人设、声音、背景、粒子、封面、头像、演示视频和可用选项，生成 B 的客户端可见部分；服务器私有人设和音色管理信息仅保留引用。
5. **构建移动端内容**：按受支持 iOS/runtime profile 预建模型、Animator、材质和纹理；计算核心/扩展依赖、大小与哈希，不把 Unity 制作、图采样或纹理压缩留到用户点击后的流程。
6. **验证与发布**：验证真实默认外观、控制恢复、口型、能力引用和成品依赖；上传全部必要对象，确认可访问和版本一致后发布目录清单。来源预处理失败的候选不进入普通用户可下载目录。

星夜交付内容至少有以下结构：

| 文件/对象 | 作用 |
| --- | --- |
| `manifest.json` | 星夜格式标识、schema/发布版本、角色 ID、资产版本、目标平台/runtime profile、最低 App 能力、能力声明、核心/扩展包依赖及文件哈希/大小 |
| `definition.json` | B 的客户端展示与运行配置：公开角色信息、背景/效果/媒体引用、可用选项及默认值、受支持互动策略；不含服务端私有提示或凭证 |
| 模型核心内容 | A 的移动端成品，包含真实默认人物显示及对话表现所需全部依赖 |
| 模型扩展内容 | 经支持和验证的额外换装、动作及效果，按需下载，引用明确版本的公共/核心资源 |
| 预览与场景媒体 | 封面、头像、图片、演示视频、背景及必要音频；独立对象，按内容用途缓存，不强制塞进模型核心包 |
| `credits.json` / 必要 notices | 保留实际资产作者、媒体来源和必须随交付附带的声明；作为规范化来源/署名资料，不伪造为星夜原创 |

OSS 对象键由星夜的稳定身份、版本和内容哈希组成，不以原 ZIP 名、SDK 文件名或机器路径作为公共目录。下列是目标布局示意，不代表已创建的 bucket/对象：

```text
starrynight/characters/<characterId>/<releaseId>/manifest.json
starrynight/characters/<characterId>/<releaseId>/definition.json
starrynight/characters/<characterId>/<releaseId>/credits.json
starrynight/avatars/<assetId>/<assetVersion>/ios/<contentHash>/core.bundle
starrynight/avatars/<assetId>/<assetVersion>/ios/<contentHash>/outfit.bundle
starrynight/media/<contentHash>/<mediaFile>
```

`sourceArchive`、原始目录、源 GUID 索引、完整 Inspector/转换日志、未知插件诊断和制作中间文件进入私有追溯记录，不进入普通客户端配置。追溯记录由生成版本/内容哈希关联，以便维护与复现；公开署名仍按素材实际来源保留。App 接受的是经过发布的星夜清单及已支持的数据/组件，不直接解析 `.unitypackage`、原始 Prefab 或源平台 SDK Controller。

面向普通用户的选项是“表情、动作、换装、背景、声音”等产品功能，下载状态是“下载、准备、就绪、更新”等；来源适配细节进入制作后台。必需能力不匹配时使用实际可操作的用户说明，例如“这个角色需要更新 App”，不把 SDK 错误、缺失 GUID 或组件类名作为产品错误文案。必要的作者署名和声明可通过素材信息入口查看，不要求把来源兼容标签放到角色卡片或首次使用流程。

网络交付使用小清单和多个可缓存对象。用户选中角色后直接下载、验证和加载预构建成品，保留前文的恢复下载、缓存复用和版本原子生效策略；不在手机上重跑源包预处理。新增超出已有运行能力的效果仍需更新 App，星夜格式不允许通过下载包安装任意代码。

优先复用现有来源封面/预览、背景、头像、音乐和已批准声音；没有图片时可由受信渲染器截取模型缩略图。本次整理不调用图片生成模型，不自动重新设计付费音色或生成音乐，也不声称动态两部分交付已经实现。

## 7. 转换服务与部署

研发阶段先在现有开发机以命令行按需转换，复用已有 Unity/Blender 工具，证明通用入口和成品加载。规模扩大后由独立转换 worker 为制作侧执行任务；普通 App 用户直接消费已发布成品。worker 不依赖旧 Mac 业务服务，worker 离线也不影响已发布角色的目录、下载和对话。

```text
制作侧 / 开发机导入入口
    → 账户服务：制作任务、来源文件授权、状态
    → 独立转换 worker：隔离审计、转换、内容构建和验证
    → 私有内容存储：源包、回执、目标平台成品
    → App：下载、安装、动态加载
```

任务状态建议为：排队 → 审计 → 等待选择/依赖（如需）→ 构建来源 → 转换 → 验证 → 就绪 / 需要处理 / 失败 / 取消。每一步有可重试回执；同一任务不会因重试重复入库或重复计费。

服务端任务/存储/worker、目录和下载授权代码属于 `../starrynight-server`；客户端保留协议、浏览/选择入口和加载实现，遵守已完成的仓库隔离。worker 工具通过明确输入输出构建，不从客户端 checkout 隐式读取运行依赖。

迁移记录中的现有业务云主机为 2 CPU、约 1.6 GiB 内存。以该配置不应与线上账户/AI 服务共跑 Unity/Blender 构建。可先让它仅管理任务和权限，转换节点单独配置；Unity 的 [Editor 系统要求](https://docs.unity3d.com/6000.3/Documentation/Manual/system-requirements.html) 与真实源包峰值共同决定机器选择。节点并发第一版从 1 个任务起步，内存/磁盘/耗时测量后再扩大，不在本次方案里采购或启动服务。

自购源包默认进入用户私有库，发布到其他用户可下载的公共库是独立操作。原始源文件保留/删除策略需在导入设置中明确；不同账户不能通过猜测任务 ID 或哈希访问私有源资产。

## 8. SDK、模型及插件许可

[SDK 官网](https://creators.vrchat.com/sdk/) 可以作为识别契约的依据，但不是把整个 SDK 放进星夜的授权。[VRChat Materials License Agreement](https://hello.vrchat.com/legal/sdk) 对 SDK 材料的平台外使用有限制，具体目录的 License File 也会影响授权。SDK 依赖参与外部构建、官方默认动作和示例资产都需要逐项核验；烘焙或换格式不会自动解决许可。已有隔离 bake 成功只证明技术路径。

作者独立模型、纹理、动画、Shader 和构建工具分别按自身许可处理。比如 [lilToon 是 MIT](https://github.com/lilxyzw/lilToon/blob/master/LICENSE)，可在遵守条款的前提下复用；模型是否允许自用、平台外使用、嵌入安装包或公开分发仍由作者许可决定。方案的自动导入入口不自动授权公共分发，也不自动开放生成式内容制作。

优先走独立来源数据解析＋星夜自有宿主行为。涉及 SDK 的已知插件构建路径应限定受支持且可使用的依赖版本；不能为了补包把作者未知代码直接执行。

| 阶段 | 具体工作 | 完成标准 |
| --- | --- | --- |
| 0：原型 | 选基础头像、复杂 FX、MA、联合包、特殊 Shader、Generic 和缺本体来源；验证单角色 iOS 成品加载及版本契约 | 至少一个新人物通过内容包出现在已安装 App 中；无需新增运行代码的第二个兼容人物不重装即可加入 |
| 1：通用识别 | 建立单次导入入口、结构化候选/依赖图、稳定 UUID 和报告；拆出批次目录/名字专用逻辑 | 测试包重命名/换目录仍识别同一资产；多个候选有正确选择；服装包不会冒充本体 |
| 2：可用人物转换 | 统一默认外观、材质、姿态与许可清楚的宿主替代；支持结果分级和缓存 | 已支持完整源包不再需要逐角色代码改动；基础脸部/服装正确；缺必需资源有可操作结果 |
| 3：客户端内容 | 动态角色注册表、下载/安装/卸载、切换、更新/回滚与离线缓存 | 角色增加不改编译名册；中断重试不破坏已有包；设置/控制/对话归属不串角色 |
| 4：发现/商城交付 | 图文、视频、选择并下载、加入自己的角色库；模型与已就绪对话身份绑定 | 用户从发现页选中角色后完成下载和对话；不参与模型转换；已有内容可离线加载 |
| 5：托管制作 worker | 独立制作任务/存储、身份与资源限制、版本化内容构建及运行观测 | 开发机离线时可继续制作/上架；制作失败不影响用户消费已发布角色 |
| 6：覆盖扩展 | 按真实高频失败补 MA、Generic、Poiyomi、约束、粒子和复杂物理适配 | 每个新增适配器有可复现来源测试并回归既有角色；能力范围明确更新 |

阶段 0 同时验证通用来源骨架和交付风险，防止先投入大量 UI 后发现成品格式不可动态加载。阶段 1/2 使用本地命令行也能交付给制作方；App 从目录下载导入须完成阶段 3/4、下载授权和 OSS 内容托管，不需要把转换 worker 放进用户请求链路。阶段 5 只用于规模化制作。阶段序号描述依赖和范围，不承诺固定工期；可在原型确认后拆解里程碑。

建议新增 `ImportManifest`、`DependencyGraph`、`CapabilityReport`、`ConversionReceipt`、`RuntimeContentManifest` 等版本化契约，以及统一的 `SourcePackageImporter`、`CharacterRegistry`、`CharacterContentLoader`。这些是设计名称，不是已存在的 API。第一版服务接口同样应按现有 `/v1`、账户隔离与 OpenAPI 风格定义，避免直接沿用客户端提供的账户/角色权限。

## 10. 验收与成本控制

使用现有 40 条来源作为回归集，另外补作者自有/许可清楚的 Generic 和最小依赖测试。通过率分别统计“来源正确识别”“人物可用”“原作控制可用”，缺本体包应被正确识别为需要补文件，不计为可用模型转换成功。

原型优先选旧琪宝作为已知基础、Ichigo 验证 FX/恢复、Shizuku 验证联合包、Ramune 验证 MA 生成引用、Milfy 验证屏幕效果降级，以及 Rindo 验证缺本体诊断，再补一个自有 Generic 来源。选择这些案例不改变已发布角色，也不意味着重做其产品媒体。

| 测试维度 | 必须看到的结果 |
| --- | --- |
| 来源稳定性 | ZIP/目录重命名、嵌套包、重复 GUID 冲突、跨文件依赖与多 Prefab 选择可解释 |
| 默认外观 | 正面/侧面脸部、衣服显隐、默认 morph、透明/描边及站姿检查 |
| 支持的控制 | 菜单/动作生效、默认恢复、口型和表情并用、取消或切角色后恢复 |
| 动态内容 | 安装、重复导入、同角色升级、中断/损坏包、淘汰重载、离线可用 |
| 账户隔离 | 私有任务/模型归属，注销/切账户不泄露源包或内容 |
| 星夜交付边界 | 公开下载使用星夜清单和资源键；客户端不接收源工程/SDK；公共配置无机器路径和制作日志；普通 UI 使用星夜功能语义，必要署名保留 |
| 性能 | iPhone 上的峰值内存、加载/切换时间、完整会话帧耗时；静态预算和模拟器不能代替 |
| 成本 | 每个包的人工作业、首次转换耗时、重复导入缓存命中、失败原因和存储量 |

自动化验证使用自有微型资产和不会调用付费模型的测试；来源包及大图像/日志留在私有目录。导入器升级缓存按工具/依赖哈希失效，公共运行时改动回归当前所有发布角色，不强行重做未变的模型。

降成本重点是统一识别、统一替代、缓存和动态内容交付。初期不逐项复刻 VRChat 的全部行为，也不追求某个未经实测的覆盖率数字。先用现有真实模型库确定最常见的阻塞原因，每补一个适配器提高一批模型的可用性，再决定下一阶段投入。

## 11. 发现/商城的内容和发布契约

列表卡片只加载缩略图、名字、作者/标签、简短介绍和可用状态。详情提供角色图片、完整基本信息、演示视频、版本及下载规模；默认不加载完整 3D 数据来生成这些预览。图片根据屏幕尺寸取合适分辨率并缓存，视频按需播放，列表滚动和页面退出时停止不再可见的播放器。

图片和演示视频在上架前生成或准备，展示最终可下载版本的默认外观和实际可用能力。优先复用获授权的作者素材和转换后的渲染结果；不自动调用图片生成模型。若来源视频的效果超出移动端版本，需换成实际版本演示或明确说明差异。

服务端已有 `GET /v1/characters`、`GET /v1/characters/{id}` 和作者目录路由，可扩展公开目录元数据。轻量目录与当前用户的订阅/使用权限分开处理，避免私人状态进入公共缓存。目录支持分页、搜索、版本/ETag 和本地缓存，详情展示不会串行等待每个大资源。

每个发布版本至少包含：

- `characterId`：现有服务端角色/对话身份；`avatarAssetId`：模型资源稳定身份；`releaseId`：不可变内容版本。
- 图片、缩略图、演示视频地址及对应尺寸/时长信息。
- 移动端 profile、最低 App 能力版本、内容构建版本、默认外观及可用控制。
- 首次显示包和扩展包的大小、依赖关系、SHA-256、压缩方式及目标平台。
- 可对话状态、声音/人设配置的服务端引用；不向客户端交付供应商 Key 或服务端凭证。

目录条目可以变化，内容版本本身不能原位覆写。发布顺序是验证成品 → 上传全部必要对象 → 检查 OSS 可达/哈希 → 原子发布目录版本，避免用户看到尚未上传完整的角色。客户端更新采用新版本候选，失败保留旧版本；制作方回滚目录指针不删除仍在使用的旧内容。

第一版实现发现页和内容授权，商城展示沿用同一目录契约；真正的收费交易可单独接入权益判断，不与模型转换混为一个工程。已有客户端发现/商城 UI 的在途修改应由其开发会话保持，本方案不覆盖这些源码。

## 12. OSS 内容交付与下载路径

OSS 保存完整移动端成品、预览媒体和所需扩展内容，来源开发包另放制作侧私有位置。普通用户不会下载原始 ZIP、SDK、未用纹理或制作中间文件。可先使用 OSS HTTPS 交付，后续接 CDN 加速并分别测试冷/热缓存，不把配置自有 CDN 域名作为最初原型的阻塞条件。

账户 API 负责目录和权限，不代理大模型字节。建议一个新内容解析接口（设计名 `POST /v1/characters/{id}/content/resolve`）一次返回兼容发布版本、Manifest、权限有效期，以及必要资源的可下载地址。用户身份来自现有会话，平台/profile/已缓存版本由请求描述；服务端拥有成品记录，不能信任用户可编辑的角色 `data` 字段直接指定任意可执行资源或下载权限。

客户端随后直接从 OSS/CDN 获取数据，避免大文件穿过现有小型账户服务器。私有 Bucket 的签名 URL/可信 CDN 鉴权由服务端提供，客户端不保存 OSS AccessKey。公共预览与受控模型内容可用不同对象前缀/访问策略。

对象键带资源 ID、版本和内容哈希，例如 `characters/<asset-id>/<release>/ios/<sha>.bundle`。内容保持不可变，媒体与成品允许长缓存；最新版本指针和用户权限用短缓存或条件请求。CDN 的缓存键与签名验证要一起测试，既避免每个用户的签名打散所有缓存，也不能通过忽略参数绕过权限。

下载器按清单已知的字节数和对象身份做续传；同一对象合并重复请求，小数量并发按实测调节。服务端签名过期时刷新授权后继续相同不可变对象，不能把新版字节拼接到旧版。处理 HTTP 200/206/416，验证 Content-Range 与对象大小；OSS/CDN 的 [Range 回源官方说明](https://help.aliyun.com/en/cdn/user-guide/object-chunking)表明相关回源需显式配置和正确范围。ETag 作为对象/续传标识，不替代清单中的 SHA-256 完整性校验。

## 13. 从选择到对话的快速应用流程

### 三条加载路径

| 情况 | 关键路径 |
| --- | --- |
| 首次选择 | 立即打开原生对话壳层/角色封面；并行准备目录和授权；下载必要成品；校验、加载、首帧显示 |
| 本地已有校验内容 | 检查版本/已有权限状态后从本地加载；不重新下载、转换或每次全量扫描所有文件 |
| 角色已在内存 | 复用当前实例、材质和 GPU 资源，恢复角色状态并转入对话；不销毁再重建 |

对话界面、封面、名字、已有消息与文本输入不等待 Unity 模型加载。账户有效且角色对话配置就绪时，可并行建立对应会话；3D 实例就绪后接替封面展示。需要区分原生对话可用和真实模型首帧，不能把封面已出现统计为 3D 已加载。

### 上架前处理和首次显示包

移出客户端热路径的工作包括源包展开、FBX/GLB 转换、骨骼采样、控制器生成、纹理缩放/压缩、材质映射、默认状态解析和内容依赖计算。成品使用 iOS 原生纹理和预构建 Animator/Prefab，避免用户点击后再进行这些制作步骤。

首次显示包包含真实人物默认外观的全部依赖闭包：默认网格、脸/身体/服装材质与纹理、站姿/基础动作、可用口型及必要控制。其他穿搭、高阶原作动作、可选音乐和额外效果可以按需下载，不要求先等整个角色档案。

拆包必须由实际资源引用和默认状态决定；不能仅按文件类型划分。核心控制器引用扩展内容时，需要改成明确的按需能力或将其依赖纳入核心包，避免“主包很小”但实际加载自动拉回全部附件。暂未下载的选项不显示为立即可用。首版先用单角色完整 bundle 验证正确性，再在原型中测出可拆分的默认闭包。

默认材质、服装和脸部质量优先保留，性能收益主要来自去除首次显示不需要的数据、预处理和缓存。较低质量 profile 如需提供，应作为明确选项，不以“快”为理由默认悄悄替换成不同外观。

### 下载后的 CPU、内存和 GPU 路径

- 避免 ZIP 外壳套 AssetBundle 导致额外全包解压。按终端总耗时实测 LZ4 与 LZMA：Unity 的 [压缩说明](https://docs.unity3d.com/6000.0/Documentation/Manual/assetbundles-compression-format.html)表明 LZ4 按块解压、LZMA 更小但访问资产需整包解压。首屏内容先测试 LZ4；弱网下更小文件可能更快，最终由下载加加载的总时间决定。
- 前台下载可边写盘边计算哈希；后台系统下载结束后在工作线程校验，禁止整包读成一个大内存对象。通过校验的不可变本地版本记录回执，下次加载不重复做全部首次安装工作；字节或元数据变化时重新验证。
- bundle 加载、纹理准备和可后台进行的检查异步执行，Unity 对象创建仍按其主线程要求处理。分帧实例化/初始化、减少首帧脚本扫描与控制器层，避免一口气阻塞原生 UI 或渲染。
- 只预热本角色真正用到的 Shader 变体和可见材质，按小批预算执行；原型同时测冷 GPU 和预热 GPU 首帧，不能用隐藏实例存在推断已上传全部 GPU 资源。
- 优先保留当前角色及一个准备中的角色，沿用内存/热状态控制；共享资源按内容哈希去重。不要因预加载目录中的所有模型耗尽手机内存。
- 在详情阶段预取轻量清单与缩略媒体；已授权且满足网络/存储预算的默认人物包可在用户停留时预取。移动网络的额外预加载应受设置控制，选中角色任务抢占背景预取。
- 快速连续选择 A→B→C 时，只有最新代次可以应用到画面/对话；过期任务取消或仅留作缓存，不覆盖当前选择。下载/加载去重与取消按使用者引用处理，避免取消一个预览同时杀掉正在使用的实例。

冷加载真实首帧时间应拆解为：授权等待、必要字节传输、未被传输阶段覆盖的校验/安装、bundle/对象加载、GPU 首次准备与首帧提交。源转换和扩展包下载不应处于这条关键路径。OSS/CDN 吞吐、网络 RTT 和移动端加载各自统计，才能知道下一项优化的收益。

### 性能验收目标

下列是 iPhone 17 原型的**初始设计目标，不是当前实测结果或对任意大小模型的保证**。原型要固定参考角色包、iOS/Unity/App 版本、网络与温度，并据数据调整最终阈值。

| 项目 | 初始目标/测量方法 |
| --- | --- |
| 点击到原生对话壳层响应 | P95 ≤ 200 ms；不等待资源下载 |
| 内存中已有角色应用 | P95 ≤ 500 ms；计入真实实例和状态恢复 |
| 已缓存成品到真实模型首帧 | P95 ≤ 1.5 s；另记包大小和内存峰值 |
| 首次必要下载完成后的应用 | P95 ≤ 2 s；只统计实际仍需的校验、加载与 GPU 阶段 |
| API 服务端处理 | 内容解析/权限处理 P95 ≤ 100 ms；端到端 RTT 另记 |
| 首次下载 | 记录必需字节量、有效吞吐、OSS/CDN 冷热缓存、续传和 RTT，不以任意统一秒数承诺 |

埋点记录选择、原生 UI、授权、首字节、下载完成、验证、Unity 加载、首帧、对话可用等时间点，并报告 P50/P95 和冷/暖缓存。头像预览、真实 3D 首帧、完整扩展内容就绪分别衡量。若目标未达，按关键路径优化，不把省略校验或错误默认状态当成优化。

## 14. 建议产品承诺

“制作侧支持作者发布的 VRChat 角色开发包，经自动转换和验证发布移动端成品。用户在发现/商城页看图文和视频，选中后下载并进入对应角色对话；缓存角色快速复用。人物默认外观优先保留，支持的表情、动作和换装继续可用，适配范围明确。”

这与用户本次目标一致。实施下一步应先打通“一位新角色预构建成品 → OSS → 已安装 App 动态加载 → 真正进入对应对话”的原型，再完善结构化来源导入、目录发布和分包预热。原型通过后对自动化覆盖、加载耗时、节点成本与里程碑做实测估算。
