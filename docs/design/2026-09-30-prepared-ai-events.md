# 真实 AI 预备事件与智能接话 · 0.66

本轮把摇晃、轻捏、轻扯、待机、初见、重新启动与回到角色的主动问候统一为真实 AI 候选。按用户最终要求，每个适用场景只准备一组，用完立即补充；“准备一半”可以交接给当前会话。输入框增加智能回复入口，提供三条按选择倾向排序的用户接话，并依次准备各自的一组 AI 回应。没有新增生产环境固定台词或本地假 AI。

## 慢在哪里，如何修复

用户实际触发记录中，一次捏扯未命中候选，首段 PCM 为 6,325 ms、规划尝试 2 次；另一条摇晃命中缓存，首段 PCM 36 ms。因而不能把“后台已启动准备”当作“前台已消费准备”。复核发现三条额外等待路径：

1. 旧池只消费完整 ready 候选，生成中的候选先被前台取消，再重新开始同一场景的付费生成。
2. 原生手势等当前生成／朗读空闲，最长 15 秒；即便服务器有音频也不能立即触发。
3. 后台准备要等朗读结束后再过 3 秒，入场协调器还可能在发送问候前取消自己的准备任务。

现在用 `PreparedDraft` 保存有界、按序可重放的事件流。前台先认领候选，再停止其他后台工作；有文字和 PCM 就立即交付，余下事件沿同一个任务继续。手势直接中断当前朗读，继续遵守手势阈值、20 秒共用冷却、录音／编辑优先规则。拿到 AI 文本后 0.2 秒便开始下一批准备；问候准备和 3D 加载重叠，切入已经预测的角色时保留生成。没有让加载动画故意延长来伪装命中。

## 统一候选和真实会话的边界

| 维度 | 实现 |
| --- | --- |
| 所有权 | 账户、角色、场景、上下文指纹；绝不跨账户借用语音 |
| 场景 | `shake`、`pinch_in`、`pinch_out`、`idle`、`first_meeting`、`app_launch`、`return` |
| 容量 | 每场景 1 组；旧值 2 自动收敛为 1；初见前只准备初见 |
| 生成 | 同一角色提示、核心规划、心声、导演、去重和流式 TTS；可选表现继续并行 |
| 实际使用 | 冷却／待机节奏通过后，原子消费候选、写入消息和去重索引、完成 request_id |
| 半成品 | 回放已经生成的事件并等待同一任务的新事件；不重复规划／合成，不等完整音频 |
| 补充 | 消费后立即启动替补；新正文到达后再次按最新上下文检查缺口 |
| 失效 | 普通对话话题、人设、音色、偏好、记忆、能力变化；手势／待机 15 分钟、入场 24 小时 |
| 生命周期 | request_id 租约防止旧页面取消新准备；切账户／角色取消无用工作，保留可复用完整候选 |

准备时不提交用户消息、AI 已说内容、长期记忆、关系变化、事件冷却或动作使用次数。候选之间只在内部新意审查中参考，不伪造 assistant 历史。真正被触发后才按当前时间写入历史、更新相处状态。准备时长不计入表演时轴；原作能力目录及多组表现通道保持通用，不对角色写特殊分支。

固定事件本身照常进入真实历史，但不因一条自动事件耗尽其他仍适用候选；普通用户对话改变上下文时重新准备。初见、重新打开 App、切回来分别使用不同任务，不能用初见台词欢迎熟悉用户，也不声称知道未知的离开时长。

## 三条智能回复

收到 AI 文本后立即请求三条适合用户说的话，优先短句且三条含义不同。模型提供相对选择倾向，客户端按高到低显示；这是启发式排序，没有声称已经学习用户行为并得到校准概率。

后台按第一、第二、第三的顺序，各执行一次正常 AI 回复流程，每条只留一组。每组内部仍是核心内容和可选表现并行、语音流式生成。用户提前选择第二或第三条时，提升选中分支并取消无用工作；如果该分支正在生成，直接接管。用户原先输入但尚未发送的草稿保留。

候选 ID、文本、来源 AI 消息、上下文和账户必须相符。只有选中的用户句与 AI 句进入聊天，另外两条及未使用音频删除。手动改写选项、换话题或使用过期 ID 会走普通对话，不误用旧答案。选择后的下一轮重新生成三条新建议。

入口采用输入框左侧的小渐变星芒；三条接话浮在输入框上方，保持角色为主体，不移动聊天区域。界面验证发现 SwiftUI 自定义 alignment guide 曾让浮层向下展开并被底栏挡住，改为参照输入框实测高度向上定位，并验证所有选项的可见范围与命中。错误提示并入原有 34 pt 工具行，最多两行小字，关闭前后聊天高度及输入位置保持不变。

## 协议、部署与费用

Go 增加受 session 保护的 `reactions/prepare|pause|status` 和 `suggestions/prepare|status` 代理白名单，并生成 OpenAPI。新增字段均可选或只出现在新接口：消息请求 `quick_reply_id`；事件 `prepared`、`preparation_inflight`；智能建议 `source_message_id`、`options`。没有新字段的旧消息重放保留原哈希，不重新收费。

候选存储在私有 AI worker 的 SQLite WAL 与私有 PCM 目录。本轮为本机单 worker；没有把它宣称为多实例队列。正式扩展应将任务租约、原子认领、事件缓冲和音频迁往共享数据库／Redis／对象存储。独立 Go 账户服务仍使用 PostgreSQL 与 Redis，无耦合到 iOS/Unity。

后台最多 4 个候选任务同时运行；智能回复的三条回答依次准备。只准备当前角色和离开会话时预测的一个入场角色，不为整个发现市场遍历生成。每个候选、建议排序、表演和 TTS 都会正常产生供应商费用，丢弃已生成分支不等于退费。可选建议只有一次结构生成，失败安静退出；失败退避按场景隔离，某个候选出错不会阻止其他场景用后立即补充；普通对话原有有界质量修订仍保留，没有添加无限重试或重新限制用户日常用量。

这不是供应商的 prompt cache：缓存的是本次上下文下完整或正在生成的真实回答及音频。手机仍需网络和私有网关；首次遇到某角色、上下文刚改变、候选已经消费而替补未生成出内容时，仍需等剩余生成过程。已经收到的 PCM 可立即接管播放，但无法保证未产生的内容瞬间出现。
