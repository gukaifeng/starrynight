# v0.7.1：动作取景的平滑弹性过渡

## 问题

旧版在动作开始时将取景目标改为全身，结束时恢复对话近景。虽然对包围盒用了 `1-exp(-18dt)` 插值，但这种曲线从第一帧就具有较高速度，没有自然起步；再把插值包围盒送入包含 max 约束的透视求解，会在主导轴改变时产生速度拐点。人物大小与竖直构图同时改变，表现为急缩和急放。

## 处理方式

- 改为先求最终透视距离与构图焦点，再对最终镜头位置进行阻尼弹簧过渡。包含沉浸式聊天的人物上移构图，避免距离变柔和但构图中心仍突变。
- 距离在对数空间计算，保持大小不一的 Luma、初音和写实女性有相近的缩放节奏。模型本体和骨骼比例不变。
- 阻尼比 0.80，单次阶跃理论超调约 1.52%。动作拉远 response 0.62 秒，恢复 response 0.82 秒；参数是弹簧固有周期，不是硬编码完成时长。实测标准阶跃约 0.342／0.450 秒完成 95% 行程，之后细微收稳。
- 精细面板、直接手势和视口调整使用更快的 0.30 秒 response，避免手势显得拖沓。用户设定仍受既有范围限制。
- 位置和速度作为持久状态保存。动作连切、中途取消或更改取景只改目标，保持当前速度；新选角色或明确要求立即复位时清除旧状态。
- 使用二阶方程的解析解，30／60／120 Hz 下同一时刻产生相同过渡。暂停恢复或卡顿时，最多推进 1/15 秒的弹簧时间，避免把长时间间隔一次变成镜头跳跃。
- 状态回执等待实际收稳，最长两秒，取代固定 0.55 秒后假定结束。桥接增加当前是否过渡、目标距离、缩放速度与 motion revision，供验收使用。

## 技术决策

采用项目内已有官方 `unity-cli` 技能驱动已打开的 Editor。新增独立的小型数学类，不增加动画插件或运行库；场景和资源仍通过 Unity 构建脚本生成，未手写场景 YAML。

Unity 的 [Mathf.SmoothDamp](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Mathf.SmoothDamp.html) 采用避免越过目标的策略，无法直接提供本次所需轻微回弹，因此使用保留速度的欠阻尼解析弹簧。不会每帧创建曲线、启动新协程或发送镜头采样消息。

保持 `contentVersion=6`，`framingProtocol` 升级到 4；构建门禁拒绝旧导出。原生版本升级到 0.7.1 / build12，手机离线语音继续随包提供。

## 验证

`FramingMotionReview.Validate()` 是导出的必要检查：缓起步、受限回弹、最终收稳、三种角色尺度、30／60／120 Hz 一致性、改目标时的位置速度连续、零时间步、后台恢复和选择新角色时清除惯性。

UI 用例 `ActionFramingMotionTests` 在三个真实角色上连续触发动作，等待自动恢复，检查原距离和用户设定；`verify_framing_motion.py` 再从真实 Unity 事件断言开始时不会瞬移、连切仍保留速度、只有最后一个动作完成、完整动作取景收稳以及最终恢复。另运行直接手势回归。记录实际模拟器视频和截图，数值曲线本身不代替视觉检查或真机持续帧率测试。

结果与证据：[动作过渡验收](../verification/framing-motion/README.md)。
